## Воспроизводимая проверка на чистой VM

Используйте отдельные VM Ubuntu 24.04 и Debian 13 с публичным IPv4 и systemd.
Для расширенной матрицы повторите на остальных заявленных версиях ОС и arm64.
Разрешите входящие 80, 443, 2053/TCP в firewall провайдера. Скопируйте исходный проект
или опубликуйте архив через `scripts/pack-release.sh`. Не используйте рабочий VPN-сервер.

1. Запустите `sudo bash scripts/install.sh`. Убедитесь, что Docker отсутствует,
   установщик автоматически ставит Docker Engine и Compose Plugin без подтверждения
   и спрашивает порт с default 2053. Повторите на отдельной VM с `docker.io` без Compose:
   конфликтующие пакеты должны замениться без очистки данных Docker. Также проверьте
   запуск уже установленного, но остановленного Docker.
2. Откройте `https://IP:2053` с другой машины. Проверьте доверенную цепочку сертификата,
   IP SAN, отсутствие HTTP и фактические статусы обоих сервисов.
3. Сохраните учётные данные. Проверьте права файлов (`0600`, каталоги `0700`),
   отсутствие логина и пароля в `docker compose logs`.
4. Повторите установку, затем перезагрузите VM. Проверьте готовность, неизменность
   имени, bcrypt-хеша администратора, ключей и сохранённых портов.
5. Остановите Xray: `docker compose stop xray`. `/health/ready` должен вернуть 503,
   `/health/live` — 200. Запустите Xray и дождитесь восстановления 200 без перезапуска Go.
6. Убедитесь, что 10085 недоступен с другой машины, а 443 отвечает как VPN-listener.
7. В отдельной тестовой установке занять 443 командой `python3 -m http.server 443`:
   установщик должен выбрать 8443. Занять 2053 — должен отказать, не занимать другой
   порт панели молча. Занять оба VPN-порта — должен завершиться ошибкой.
8. Закрыть 80/TCP снаружи: `TLS_MODE=acme` должен завершиться ошибкой без ложного
   сообщения об успешной установке. `TLS_MODE=auto` должен предложить резервный HTTPS.
   При `NONINTERACTIVE=1` без `ALLOW_SELF_SIGNED=1` переход должен быть запрещён.
9. На машине без публичного IPv4 установщик должен отказать; `PUBLIC_IP=127.0.0.1`,
   private, multicast, documentation и CGNAT-адреса должны быть отклонены.
10. Прервать установку после инициализации SQLite, затем повторить. Данные и ключи
    сохраняются, ожидающие передачи учётные данные доступны.
11. Проверить `systemctl list-timers proxyk-admin-renew.timer`. После успешной выдачи
    выполнить репетицию продления **на тестовой VM**:

    ```bash
    sudo docker run --rm -p 80:80 \
      -v /opt/proxyk-admin/acme:/etc/letsencrypt \
      certbot/certbot:v5.9.0 renew --dry-run --cert-name proxyk-admin
    ```

    `--dry-run` не заменяет проверку фактической автоматической ротации: дождитесь
    окна продления короткого сертификата и сравните serial/NotAfter сертификата,
    полученного внешним TLS-клиентом, без перезапуска Go. Проверьте ошибку timer
    при закрытом порте 80 и последующее восстановление.
12. Повторить установку через выпущенный `curl | sudo bash`, убедиться, что ввод
    читается с терминала. Повреждённый SHA-256 архива должен остановить установку.

## Что не проверяется на этапе 1

- Импорт VLESS URI, реальный VPN-трафик, расход лимитов: этапы 2 и 4.
- Веб-авторизация, cookie, CSRF, rate limiting: этап 3.
- Online backup, restore, обновление с rollback: этап 4.

Пустой REALITY inbound на этапе 1 не выдаёт пользовательских подключений.
Его TLS target `www.cloudflare.com:443` должен быть проверен на конкретном VPS перед
включением пользователей на этапе 2; доступность target зависит от сети сервера.

## Ранее проверено для v0.2.0

`scripts/test-native.sh` проверяет CLI и трафик на Xray 26.10.31. Для теста TLS-цель
REALITY и HTTP-сайт работают на loopback. Проверены создание пользователя, передача
трафика с параметрами выданной ссылки, чтение обоих счётчиков, сохранение ключа при
переименовании, запрет новых подключений после отключения и удаления, восстановление
активного пользователя после перезапуска Xray и удаление устаревшего аккаунта после
перезапуска приложения. Через VPN-подключение служебный gRPC-порт Xray недоступен.

Тест SQLite применяет новую миграцию к базе этапа 1 и проверяет сохранность настроек,
администратора и записей пользователей после повторного открытия базы.

Переход с v0.1.2 на v0.2.0 проверен в отдельном проекте Docker Compose с v0.1.2 из
опубликованного архива. При искусственной ошибке после миграции вернулись прежняя
база и образ приложения. Повторное обновление успешно применило миграцию. Проверены
команды `vpn-user list`, `create` и `link`, сохранность учётных данных, `.env`,
сертификата и конфига REALITY. Контейнер Xray сохранился при обоих переходах.


## Дополнения этапа 2 в текущих исходниках

Изменения пока не опубликованы отдельным релизом. Миграция `0003` добавляет лимиты,
накопленный трафик, даты, причины блокировки и подтверждение применения изменений.
Архивы опубликованного v0.2.0 не изменены.

8 ноября 2026 в текущей среде повторно пройдены `make test` (сборка frontend,
Go race tests, vet и проверки установщика), `scripts/test-native.sh` с настоящим
Xray 26.10.31 и Docker Compose smoke-тест с официальным образом Xray.
Сборка Linux ARM64 также прошла; запуск на ARM64-устройстве не проверялся.
Проверены следующие сценарии:

- SQLite: сохранность пользователей и доступа при миграции с v0.2.0, отдельные
  upload/download, отсутствие двойного начисления при повторе порции, нулевой и
  неограниченный лимиты, снижение/повышение лимита и защита от переполнения счётчиков.
- Бизнес-логика: повтор после сбоя записи, восстановление журнала после остановки,
  запрет второго сборщика, обработка повреждённого журнала, подтверждение только
  применённой версии записи, сохранение незавершённого создания и запрет выдачи
  ссылки до проверки работающего Xray.
- QR: PNG декодируется независимой библиотекой обратно в точную VLESS-ссылку,
  включая имя с кириллицей и специальными символами.
- Настоящий Xray 26.10.31: VLESS/REALITY передаёт HTTP-данные; расход переживает
  перезапуск Xray и приложения; второй пользователь не получает чужой расход.
  Лимит автоматически отзывает новые подключения, остаётся после перезапусков;
  повышение лимита требует явного включения пользователя. После остановки приложения
  создание/удаление не сообщают об успехе, ожидающие изменения применяются при запуске.
- В отдельном потоке данных проверяется выбранное ограничение: туннель, открытый до
  блокировки, продолжает передачу; новое подключение того же пользователя отклоняется.

Учёт имеет окно потери при аварии между сбросом счётчиков Xray и сохранением порции;
обычная задержка составляет около двух секунд, при сбоях она увеличивается. Уже
открытые туннели могут превысить лимит без верхней границы. Это согласованное поведение,
а не проверка строгого отключения всех соединений. Подробности — в README.

Реальные клиентские приложения Windows/Android/iOS, внешний VPN-маршрут с публичного
VPS, чистые VM и публичный ACME здесь не проверены. Локальный end-to-end тест использует
настоящие сервер и клиент Xray с параметрами выданной ссылки и локальной TLS-целью.
